# lyric-i18n

批量把歌词翻译成中文，写回音频文件的**内嵌歌词字段**（`©lyr`），
面向 iPod 这类**只能显示静态纯文本、没有任何渲染层**的设备。

```powershell
# 图形界面（推荐）
lyric-i18n-gui

# 命令行
lyric-i18n scan  "D:\Music"           # 先看会发生什么（只读）
lyric-i18n run   "D:\Music" --dry-run # 试运行
lyric-i18n run   "D:\Music" --out "D:\Music_已翻译"   # 写到另一个目录，源文件不动
```

---

## 为什么需要它

iPod 没有 App、没有屏幕数据库、不认外挂 `.lrc`。
在它面前，**译文唯一的载体就是 `©lyr` 那段纯文本本身**。

这也解释了为什么现成的方案都套不上：播放器侧翻译、缓存进数据库、
外挂 `<歌名>.zh.lrc`——**它们都假设对面有个能渲染的东西**。

所以这个工具做的事情很窄：**把翻译可靠地写进那个字段，并保证不错位。**

---

## 安装

需要 Python 3.10+。依赖只有 `mutagen` 一个，GUI 用标准库的 tkinter。

```bash
pip install .
```

或者不安装、直接跑：

```bash
pip install mutagen
python -m lyric_i18n.gui
```

翻译需要一个大模型的 API Key（默认 DeepSeek，很便宜）：

```powershell
$env:DEEPSEEK_API_KEY = "sk-..."
```

## 用法

### 图形界面

```
┌─ 音乐目录 + 扫描 ──────────────────────────────────┐
├─ 翻译设置（后端 / 模型 / Key / 风格 / 露骨度）──────┤
├─ 输出：☐ 原地覆盖源文件   [输出目录______] [浏览] ─┤
├─ 歌曲列表          │  歌词预览                     │
│  状态·歌曲·可译行   │  深色=原文，蓝色=译文          │
├─ 按钮条 + 进度条 ──────────────────────────────────┤
└─ 日志 ─────────────────────────────────────────────┘
```

两个值得一提的地方：

- **不用导入 iTunes 就能看歌词。** 点左边任意一首，右边直接显示它当前的
  `©lyr`，原文深色、译文蓝色。译文对不对味，当场就能判断。
- **默认不覆盖源文件。** 译文写到 `<源目录>_已翻译`，源库一个字节都不动。
  确认满意了，再勾「原地覆盖」。

| 按钮 | 作用 |
|---|---|
| `翻译选中` / `翻译全部` | 动手翻译 |
| `核对` | 拿备份当基准找漏译 |
| `从备份还原` | 一键回滚 |
| `清空缓存` | 删掉译文缓存，下次重新调 API |
| `清除处理记录` | 删掉备份目录（**删了就还原不了了**） |

### 命令行

| 命令 | 作用 | 写盘 |
|---|---|---|
| `scan` | 报告每首歌会翻多少行、跳过什么 | 否 |
| `run` | 翻译并写回 | **是**（有 `--dry-run`） |
| `check` | 拿备份当基准核对漏译 | 否 |
| `restore` | 从备份还原 | **是** |
| `prune` | 缓存维护（`--purge` 全清） | 否 |
| `forget` | 清空处理记录 | **是** |

`run` 常用参数：

| 参数 | 说明 |
|---|---|
| `--dry-run` | 只演示，不写盘 |
| `--out DIR` | 输出到指定目录，源文件不动 |
| `--only 关键词` / `--limit N` | 只处理一部分 |
| `--redo` | 用备份里的原始版本重翻（**没有备份时会拒绝执行**） |
| `--backend echo` | 离线假翻译，不需要 Key，用来验证流程 |
| `--style` | `poetic`（默认）／`literal`／`euphemistic` |
| `--explicit` | `soften`（默认）／`keep`／`mask` |

## 几个关键设计

这些都是实际踩过坑之后定下来的，不是拍脑袋。

### 歌曲身份取自**内嵌标签**，不取文件夹路径

真实音乐库里，路径和标签经常对不上：

| 文件夹说 | 标签说 |
|---|---|
| `Abel Tesfaye\` | 艺人 = `The Weeknd`（本名 vs 艺名） |
| `Compilations\...\` | 艺人 = `方大同`（"合辑" vs 歌手） |
| `...(feat. Fut` | `...(feat. Future & ...)`（长名被截断） |

所以身份一律从标签算：`hash(艺人, 专辑, 音轨号, 标题)`。
同一首歌放在哪、叫什么名字，算出来是同一个 key。

顺带，标签里的 `流派` / `年份` 直接当作翻译时的风格锚点。

### 拟声词不翻

`Oh-oh`、`La-la-la`、`Baby-baby-baby`、`ㄅㄆㄇㄈ` 这类，
翻出来是「哦-哦」「啦-啦-啦」——**把整首歌毁掉**。

三道防线：

1. **代码**：高置信度的规则先拦掉（纯重复、纯注音符号、整行全是感叹词）。
2. **提示词**：要求模型把拟声词、人名、品牌名原样返回。
3. **渲染**：译文与原文相同就不输出译文行。

关键是这三道**松紧度不同**：代码那层宁可漏判也不能误判
（误判会让真歌词被静默跳过），所以规则写得很保守；
漏掉的由后两道兜住。

### 副歌必须统一

同一句原文在歌里出现七八次是常事。逐行送翻时，模型会在第二、三次
给出**不一样**的译文——它每次都在重新斟酌。

所以：**强制统一到首次出现的译文**，并统计"纠偏了多少处"作为质量指标。

### 已翻译的歌要能认出来

导入一首别处翻好的歌（没有备份），如果当成未翻译处理，
会在已有译文后面**再插一条**，把歌词写坏。

判据是"交替模式"：原文行占比 ≥35% 且 原文行后面紧跟中文行的比例 ≥60%。

**中文歌检测不了**——中文歌里夹英文钩子是常态，"英文行后面跟中文行"
是歌本身的结构，不是翻译证据。这一条由备份判定兜底。

### 幂等与"重做"

两道判定，缺一不可：**有备份** / **形态上已是双语**。

`--redo` 的语义是"拿原始版本重翻一遍"，所以**必须有备份**。
没有备份就没有原始版本，拿现在这份（可能已是双语的）再翻只会叠加——
这种情况直接拒绝执行，而不是放任它把文件写坏。

## 安全

**写盘前一定先备份**，存在音乐目录下的 `.lyric_i18n_backup/`，
按歌曲身份命名，**首次为准**（反复翻译不会覆盖掉最初那份）。

写盘是**原子**的：先复制到临时文件、改临时文件、再整体替换。
中途崩溃不会留下半个坏文件。

用 `--out` 指定输出目录时**不产生备份**——源文件压根没被碰过，
备份的意义（写坏了能回退）在这里不存在。

```bash
lyric-i18n restore "D:\Music"          # 先看有多少份
lyric-i18n restore "D:\Music" --yes    # 确认执行
```

> iTunes / Apple Music 开着的时候可能锁住文件，写盘会明确报错而不是静默跳过。
> 改完需要在 iTunes 里重新导入才会生效。

## 常见问题

**缓存清不掉？**
「清空缓存」清的是**已翻译的译文**（`lyric_i18n.db`）；
「清除处理记录」清的是**备份目录**。两者不同，界面上都写明了后果。

**为什么有些歌被跳过了？**
`scan` 会说明原因：已有备份 / 已是双语形态 / 要求重做但没有备份。
都不想要就加 `--redo`，但**重做需要备份**。

**中文歌的译文没被识别出来？**
上面说过：中文歌的"已翻译"检测在原理上做不到。有备份的歌不会受影响。

**费用？**
约 2000 token 是每次调用的固定开销（系统提示词），一首歌一次调用。
按 DeepSeek 的价钱，**70 首大约几美分**。改提示词后重跑也是这个量级。

## 已知限制

- 只支持 `m4a` / `m4b` / `mp4`。mp3（ID3 USLT）、flac 未实现。
- 逐首串行调用，没有并发。
- 不做带时间轴的歌词输出（iPod 用不上，要导出 `.lrc` 得另做）。
- 中文歌的"已翻译"检测做不到（见上）。
- 只在 Windows 上实测过。代码本身是跨平台的，GUI 用的 tkinter。

## 开发

### 自检

```bash
python tools/selftest_clean.py      # 不需要联网，覆盖分类/拟声/重复/已翻译检测
python tools/selftest_english.py    # 需要 DEEPSEEK_API_KEY，验证英文行的取舍
```

不是 pytest 风格——它们会打印逐条结果，方便直接看出哪条挂了。

### 诊断脚本

改提示词、排查问题时用得上（都在 `tools/`）：

| 脚本 | 用途 |
|---|---|
| `dump_prompt.py` | 把渲染后的完整提示词导成可读文本 |
| `scan_clean.py <目录>` | 看分类结果、拟声清单、重复率 |
| `find_english.py <目录>` | 找出日文歌里的整行英文 |
| `check_translated.py <目录>` | 列出被判为"已翻译"的歌，人工复核误判 |
| `registers.py <库文件>` | 看每首歌的语域判定 |
| `db_info.py <库文件>` | 看缓存库里存了什么 |
| `showtags.py <目录>` | 看音频的内嵌标签 |
| `audit.py` / `gaps.py` | 拿一份基线快照对账，查漏译 |

会写文件的只有 `dump_prompt.py`（输出一份提示词文本），其余都是只读的。

### 改提示词要注意的事

提示词在 `lyric_i18n/translate.py`，改动后**必须提升 `PROMPT_VERSION`**，
否则缓存会返回旧产物。

另外，写规则时**两侧的例子要对称**——这是踩过三次的坑：
模型是按例子学的，不是按规则学的。给"该保留"那侧写六个例子、
"该翻译"那侧只写一句抽象标准，它就会全给你保留。
